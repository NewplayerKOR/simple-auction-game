# 공통 문서 및 작업 운영 규칙

> **버전:** v2.0.0  
> **상태:** APPROVED  
> **적용 대상:** 모든 역할과 AI 세션  
> **최종 수정일:** 2026-08-21

## 1. 목적

문서를 사람과 AI 세션의 외부 기억장치로 사용한다. 세션이 망각하거나 컨텍스트가 압축되어도 현재 상태, 결정, TASK, 검증 증거를 다시 읽고 동일한 기준으로 작업할 수 있어야 한다.

## 2. 핵심 원칙

### 2.1 사용자는 목표를 지정하고 문서는 세션이 찾는다

- 사용자는 문서 경로를 알 필요가 없다.
- 역할이 없으면 요청 성격으로 자동 판정한다.
- 복합적이거나 불명확한 요청은 PM이 먼저 분류한다.
- 상세 라우팅은 루트 `AGENTS.md`를 따른다.

### 2.2 현재 상태와 과거 기록을 분리한다

- 현재 사실: `docs/PROJECT_STATE.md`
- 현재 작업: `docs/common/TASKS.md`, `docs/tasks/active/`
- 완료 작업: `docs/tasks/archive/`
- 릴리즈 결과: 릴리즈 단위 기록

과거 문서의 완료 선언을 현재 상태로 추정하지 않는다.

### 2.3 문서별 책임을 중복하지 않는다

- PRD: 제품 요구사항
- DECISIONS: 승인 또는 미결정 정책
- Architecture/Data: 기술 계약
- TASK: 작업 범위와 인수 조건
- QA Plan: 검증 방식
- Project State: 현재 판정

동일 내용을 복사하지 않고 ID와 링크로 연결한다.

## 3. 문서 권위와 충돌 처리

문서 권위는 `AGENTS.md`의 순서를 따른다. 충돌 시 다음 절차를 사용한다.

1. 충돌 문장과 근거 위치를 확인한다.
2. `CONTRACT_CONFLICT`로 활성 TASK에 기록한다.
3. 제품 정책이면 PM, 기술 계약이면 ARCH_DATA에 결정 요청한다.
4. `DECISIONS.md`가 `APPROVED`가 될 때까지 관련 구현을 중지한다.
5. 승인 후 PRD·TASK·상세 명세의 링크와 표현을 동기화한다.

## 4. 역할과 책임

| 역할 | 핵심 책임 | 완료 권한 |
| :--- | :--- | :--- |
| PM | 요구사항, 범위, 우선순위, 제품 결정, 릴리즈 | 마일스톤·릴리즈 승인 |
| ARCH_DATA | Architecture, FSM, 도메인·데이터·저장 계약 | 기술 계약 승인 |
| DEV | 승인된 TASK 구현과 자체 검증 | `DEV_COMPLETE` |
| QA | 독립 검증, 결함 보고, 회귀 판정 | 개별 TASK `DONE` |
| ART/SOUND | 승인된 에셋 명세와 산출물 | 역할 인계 완료 |

PM은 코드를 작성하지 않고, QA는 제품 코드와 제품 테스트를 수정하지 않는다.

## 5. 작업 생명주기

```text
BACKLOG
  -> READY
  -> IN_PROGRESS
  -> DEV_COMPLETE
  -> QA_IN_PROGRESS
  -> DONE
```

| 상태 | 의미 | 변경 권한 |
| :--- | :--- | :--- |
| BACKLOG | 범위 또는 결정이 준비되지 않음 | PM |
| READY | 요구사항·결정·AC가 준비됨 | PM + ARCH_DATA |
| IN_PROGRESS | 구현 진행 중 | DEV |
| DEV_COMPLETE | 구현과 자체 검증 완료 | DEV |
| QA_IN_PROGRESS | 독립 검증 진행 중 | QA |
| DONE | 필수 AC와 회귀 검증 통과 후 TASK 최종 완료 | QA |

결함이 발견되면 적절한 이전 상태로 되돌린다. 체크박스는 증거를 대체하지 않는다.

마일스톤·릴리즈는 개별 TASK와 별도로 다음 상태를 사용한다.

```text
PLANNED -> RELEASE_CANDIDATE -> PM_RELEASE_APPROVED -> RELEASED
```

- QA는 개별 TASK의 최종 완료 권한을 가진다.
- PM은 완료된 TASK를 재승인하지 않는다.
- PM은 범위, 제외 항목, 알려진 제한사항과 사용자 가치를 종합해 마일스톤·릴리즈를 승인한다.
- 릴리즈 승인은 QA 검증을 반복하는 절차가 아니다.

## 6. TASK 생성 기준

작은 문서 수정은 `TASKS.md` 항목으로 관리할 수 있다. 다음 중 하나라도 해당하면 별도 TASK 문서를 만든다.

- 여러 역할이 참여함
- 여러 모듈 또는 데이터 계약에 영향이 있음
- 상태 전이·저장·마이그레이션이 변경됨
- 독립 QA 절차가 필요함
- 다음 세션으로 인계될 가능성이 높음

별도 TASK는 `docs/tasks/TASK_TEMPLATE.md`를 사용한다.

## 7. 완료 증거

완료 기록에는 최소한 다음이 있어야 한다.

- 변경 파일
- 실행 명령
- 통과·실패 결과
- 테스트 유형: 정적, 단위, 통합, 브라우저 E2E, 수동
- 미검증 범위
- 알려진 제한사항
- QA 재현 절차

`Applied`, `Passed`, `Completed`, `Production-ready`는 해당 의미를 직접 증명하는 증거가 있을 때만 사용한다.

## 8. 컨텍스트 압축·망각 복구

세션이 이전 대화를 충분히 기억하지 못하면 추정하여 이어가지 않는다.

1. `AGENTS.md`를 다시 읽는다.
2. `PROJECT_STATE.md`를 다시 읽는다.
3. 활성 TASK의 현재 상태와 마지막 작업 기록을 읽는다.
4. 연결된 승인 결정과 계약을 확인한다.
5. 실제 파일과 테스트로 값싼 최신 검증을 수행한다.
6. 불확실한 내용은 `미검증`으로 표시한다.
