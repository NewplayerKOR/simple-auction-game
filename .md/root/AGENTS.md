## 0. 문서 체계와 권위

- 활성 문서 체계는 `.md/`다.
- 구 `docs/`는 2026-11-08 `.md/`로 이관한 뒤 삭제했다. 이관 전 상세 이력은 Git과 `.md/root/archive/TASKS_PHASE_01.md`에 보존한다.
- 작업 보드는 `.md/root/TASKS.md`, 기능 명세는 `.md/root/FEATURES.md`, 역할 문서는 `.md/roles/`, 기술 명세는 `.md/specs/`를 사용한다.
- 문서가 충돌하면 사용자의 최신 명시적 지시를 최우선으로 한다.
- 같은 내용을 여러 문서에 복사하지 않는다. 각 문서는 ID와 링크로 연결한다.

## 1. 기본 원칙 (Core Rules)

1. 문서 확인 우선: 
   - 세션 시작 시 `.md/root/AGENTS.md`와 배정된 역할 문서(`.md/roles/{ROLE}.md`)를 먼저 확인한다.
   - `.md/specs/PROJECT_STATE.md`에서 현재 확인된 사실과 미검증 범위를 확인한다.
   - `.md/root/TASKS.md`에서 진행·대기·보류 상태와 담당 업무를 확인한다. PM은 활성 업무(진행·대기·보류) 전체와 블로커를 확인한다.
   - `.md/root/FEATURES.md`는 관련 기능을 조회하고, 과거 판단·결함·검증 근거가 필요한 경우에만 해당 완료 보관 기록을 조회한다. 보관 파일 전체를 매 세션 필독하지 않는다.

2. 언어 및 한국어 작성 스타일 (Language & Korean Style Guide):
   - 기본 언어: 코드 주석, 커밋 메시지, 마크다운 문서는 한국어(KR) 작성을 원칙으로 한다.
   - 인코딩: 문서와 콘솔 로그는 UTF-8을 사용한다.
   - 번역투 및 수동태 금지: 피동/이중 피동 표현을 지양하고 능동형을 사용한다. 영어 직역투 대명사(그것, 이것 등)를 남발하지 않는다.
   - 문체 일관성: 주석 및 기술 문서는 간결한 개조식 종결('~함', '~음') 또는 평서형('~한다')으로 통일한다.
   - 기술 용어 표기: 업계 표준 기술 용어(Promise, State, Props, Hook, Endpoint 등)는 억지로 한글 번역하지 않고 영문 원어 그대로 작성한다.
   - CJK 오염 방지: 불필요한 중국어/일본어 한자 혼입 및 문자 깨짐 현상을 반드시 점검 후 저장한다.
   - 원어민 문맥 퇴고: 문장을 저장하기 전 한국어 원어민 개발자 관점에서 문맥이 어색하지 않은지 검토한다.

3. 코드 무결성 유지:
   - 요청한 작업 범위에 필요한 코드·주석·설정은 최소한으로 수정할 수 있다. 관련 없는 코드와 다른 작업자의 변경은 보존하고, 삭제·축약을 변경 목적과 무관하게 수행하지 않는다.
   - 명시적인 요청이 없는 대규모 리팩토링이나 디렉터리 구조 변경을 금지한다.

4. 작업에 맞는 검증과 완료 기준:
   - 코드를 작성한 것만으로 작업을 완료로 간주하지 않는다. 코드·설정 변경은 영향과 DoD에 맞는 실행·타입 검사·빌드·테스트를 직접 수행하고 결과를 확인한다. 빌드 성공만으로 기능·연동·운영 검증을 대신하지 않는다.
   - 문서·기획·조사 작업은 내용 정합성·UTF-8·링크·근거 자료와 해당 DoD를 확인한다. 제품 코드와 무관한 작업에 불필요한 빌드나 전체 테스트를 강제하지 않는다.
   - 검증 기록에는 실행한 명령 또는 확인 방법, 대상 리비전/검토 시점, 실제 결과와 검증 범위, 증거 경로 또는 출처, 미실행 사항과 제한을 남긴다. 테스트가 있으면 통과·실패·건너뜀 수를 구분하며 과거 실행을 이번 검증으로 대체하지 않는다.
   - 필수 검증을 수행할 수 없거나 DoD가 충족되지 않으면 완료 처리하지 않는다. 통과시키기 위한 기대값 약화·테스트 삭제·skip/xfail 추가를 금지한다. 요구사항 변경으로 검사를 바꿀 때는 변경 근거와 대체 검증을 기록한다.
   - [x]는 해당 작업의 DoD와 기록된 검증 범위에 대한 완료다. 개발 자체 검증, 독립 QA, 배포·운영 수락을 구분한다.
   - `DONE` 처리는 모든 역할군이 가능하다. 단, 해당 TASK의 DoD와 검증 증거를 충족해야 하며, 다른 역할의 미완료 작업을 증거 없이 완료 처리하지 않는다.

5. 보안 준수:
   - API Key, DB 비밀번호, 토큰 등 민감한 자격 증명과 .env의 실제 값은 어떠한 마크다운 문서에도 기록하지 않는다.

6. 역할 준수:
   - 세션에 할당된 역할 문서(`.md/roles/{ROLE}.md`)가 존재할 경우, 해당 역할의 권한과 제약 사항을 엄격히 따른다. 공통 규칙은 이 문서에서 관리하고 역할 문서에는 역할별 책임과 차이만 기록한다.
   - 활성 역할은 PM, DEV, QA_DEVOPS다. 구 `ARCH_DATA` 역할은 `GOV-003`으로 종료했고, 기술 명세 작성은 DEV, 제품 결정은 PM, 독립 검증은 QA_DEVOPS가 담당한다.

7. 조사와 질문:
   - 파일·코드·설정에서 확인할 수 있는 사실은 먼저 조사한다. 작업 범위·정책·중요한 계약이나 사용자 선택에 영향을 주는 모호함은 질문한다. 그 외에는 승인 범위 안에서 합리적으로 판단하고 중요한 가정을 기록한다.

8. 우선순위와 작업 상태:
   - P0: 즉시 대응이 필요한 서비스 중단·데이터 손실·중대한 보안 문제. P1: 주요 기능 오류·핵심 요구사항. P2: 경미한 오류·개선·선택 사항. 결함이라고 모두 P0로 지정하지 않고 영향과 긴급도를 판단한다.
   - 담당 범위에서 해결을 계속할 수 있으면 [-]를 유지한다. 외부 의존성·필수 정보/환경 부족·다른 담당자의 수정 등으로 다음 작업을 진행할 수 없으면 [!]로 표시하고 원인·다음 담당·해제 조건을 기록한다. 테스트 실패 자체를 곧바로 블로커로 간주하지 않는다.
   - `DONE`은 모든 역할군이 처리할 수 있다. 완료 권한은 역할이 아니라 DoD와 검증 증거로 판정한다.

## 2. 문서 관리 체계 (Docs Governance)

- `.md/root/TASKS.md`: 진행·대기·보류 업무를 관리하는 유일한 활성 작업 지시서. 별도의 활성 작업 보드는 만들지 않는다. 최근 완료 요약과 Phase별 보관 목록도 이 파일에서 관리한다.
- `.md/root/archive/TASKS_PHASE_01.md` 등: 완료된 작업 상세 원문을 보관하는 Phase별 파일. 경로는 `.md/root/`를 기준으로 한다. 보관 파일에는 완료 기록만 넣고 신규 지시·진행 상태는 TASKS.md에서 관리한다.
- Phase 및 작업 ID: 첫 Phase는 01이며 프로젝트 진행에 따라 증가시킨다. 작업마다 프로젝트 내 고유 작업 ID·Phase·담당·목표·완료 기준(DoD)을 명시하고, 보관 후에도 작업 ID를 변경하거나 재사용하지 않는다.
- 보관 시점: Phase 전체 완료를 기다리지 않고 각 작업 완료 시 해당 Phase 파일에 원문을 보관한다. TASKS.md에는 최근 완료 요약을 완료 시각 내림차순으로 최대 5개 유지한다. 초과 요약을 제거해도 보관 원문은 유지한다.
- `.md/root/FEATURES.md`: 구현·검증된 사용자 기능의 현재 명세와 중요한 변경 요약. 기능 추가뿐 아니라 버그 수정으로 사용자 동작·API 계약이 바뀐 경우에도 기존 명세를 갱신한다. 작업 원문과 상세 검증 이력은 Phase별 보관 파일에 유지한다.
- `.md/specs/PROJECT_STATE.md`: 현재 확인된 구현·검증·제한·다음 판단만 기록한다.
- `.md/specs/PRD.md`: 제품 요구사항과 인수 기준. `.md/specs/DECISIONS.md`: 제품·기술·거버넌스 결정.
- `.md/specs/`: PROJECT_STATE, PRD, DECISIONS, ARCHITECTURE, DATA_SCHEMA, MIGRATIONS, DEV_GUIDELINE, QA_TEST_PLAN, ART_ASSET_SPEC, SOUND_SPEC, GLOSSARY.
- `.md/roles/`: PM, DEV, QA_DEVOPS 역할 문서.
- 구 `docs/`: 2026-11-08 이관 후 삭제됨. 새 작업에서 참조하지 않는다.

### TASK 생성 기준

다음 중 하나라도 해당하면 별도 TASK 문서를 만든다.

- 여러 역할이 참여한다.
- 여러 모듈 또는 데이터 계약에 영향을 준다.
- 상태 전이·저장·마이그레이션이 변경된다.
- 독립 QA 절차가 필요하다.
- 다음 세션으로 인계될 가능성이 높다.

작은 문서 수정은 `TASKS.md` 항목으로 관리할 수 있다. 별도 TASK 템플릿 파일을 두지 않고 다음 형식을 사용한다.

- `TASKS.md` 항목: TASK ID, 우선순위, 담당, Phase, 목표, 선행·블로커, DoD, 참고 링크.
- 작업 기록: 날짜·역할, 확인한 사실, 변경 파일, 실행 명령, 결과, 미검증 범위, 결함·충돌, 다음 시작 지점.
- 완료 원문: `.md/root/archive/TASKS_PHASE_n.md`에 보관하고 `TASKS.md`에는 최근 완료 요약만 남긴다.

## 3. 작업 라이프사이클 (Workflow)

1. 일감 선택: `.md/root/TASKS.md`에서 본인의 역할군에 맞는 작업을 확인하고 상태를 `[-]`로 변경한다.
2. 구현 및 검증: 작업에 명시된 DoD를 충족하도록 수행하고, 기본 원칙의 작업 유형별 검증과 결과 기록 기준을 적용한다.
3. 완료 원문 보관: DoD 및 검증 조건을 충족하면 완료 작업 작성자가 해당 작업을 `[x]` 완료 기록으로 정리하고, 상세 원문을 `.md/root/archive/TASKS_PHASE_n.md`에 보관한다. 작업 ID·Phase·담당·목표·DoD, 진행 결과·실패/판단 이력·검증 명령과 결과·증거 경로·검증 범위 및 미실행 사항을 보존한다. `DONE` 처리는 작성자 역할과 관계없이 모든 역할군이 수행할 수 있다.
4. 보관 확인 및 요약: 원문 보존과 보관 링크를 확인한 뒤 TASKS.md의 해당 상세 항목을 짧은 완료 요약으로 교체한다. 요약에는 작업 ID·제목·완료일·핵심 결과·검증 범위·원문 링크를 남기고 최근 5개만 유지한다. 보관에 실패하면 TASKS.md 원문을 먼저 지우지 않는다. 진행·대기·보류 작업은 보관하지 않는다.
5. 보관 목록 및 검수: 해당 Phase 파일을 TASKS.md의 Phase별 보관 목록에 연결한다. 작성자가 보관과 요약 전환을 수행하고, PM은 원문 누락·링크·최근 5개 제한을 검수한다. 보관된 완료 기록을 정정할 때는 날짜와 사유를 덧붙이고, 후속 작업은 새 작업 ID로 등록해 기존 기록을 참조한다.
6. 기능 반영: 사용자 기능 추가 또는 사용자 동작·API 계약 변경이 있으면 FEATURES.md의 현재 명세와 필요한 변경 요약을 갱신한다. 작업 원문·실패·상세 검증 이력은 Phase별 보관 파일에 유지한다.
